HIT Paths in Code

What a higher inductive type asks of you when you define it, when you map out of it, and when you use a path like loop. Code-first, in cubical-Agda flavour.

The one thing to hold Defining a HIT asks you to prove nothing — you just list constructors. The obligations appear when you map out: one clause per constructor, and for a path constructor you owe a path ("respect the identification"). The groupoid laws on paths come free from the identity type.

Defining a HIT: no laws to prove

A HIT is the free type generated by its constructors — points, then paths, then higher paths — just as ℕ is free on zero/suc. The circle:

data S¹ : Type where
  base : S¹
  loop : base ≡ base        -- a PATH constructor: its endpoints are earlier points

You do not prove associativity, unit laws, or anything else. The typechecker only checks well-formedness: strict positivity (as for any inductive type), and that each path constructor's endpoints (and, for higher constructors, its boundary square/cube) are well-typed. That is the whole contrast with defining a category, where you must supply proofs of the axioms. A HIT lists generators; the laws (loop ∙ loop, sym loop, associativity) are automatic from ≡.

A loop is a path value

loop : base ≡ base is an ordinary inhabitant of an identity type, so you use it like any path:

loop            : base ≡ base      -- go around once
loop ∙ loop     : base ≡ base      -- twice   (composition)
sym loop        : base ≡ base      -- backwards
refl            : base ≡ base      -- don't move
transport (λ i → C (loop i)) x     -- transport a value along loop
ap f loop       : f base ≡ f base  -- push loop through f

Mapping out of a HIT: the obligation per constructor

To define f : S¹ → X you give a value for each constructor. For base, a point of X; for loop, a path in X with matching endpoints:

S¹-rec : (x : X) → (ℓ : x ≡ x) → (S¹ → X)
   base ↦ x
   loop ↦ ℓ

double : S¹ → S¹
double base     = base
double (loop i) = (loop ∙ loop) i    -- OBLIGATION: send loop to a path base ≡ base

The path constructor forces you to say where the path goes. That clause is "the program using the loop."

The circle is ℤ (and where ua succ comes from)

The payoff: a loop is a winding number, and composing loops is integer addition.

winding : (base ≡ base) ≃ ℤ
   refl ↦ 0 ,  loop ↦ 1 ,  loop ∙ loop ↦ 2 ,  sym loop ↦ -1

This is built with the Cover family, and here is the pipeline behind ua succ:

-- 1. succ : ℤ → ℤ is PROVED to be an equivalence (inverse pred, round-trip proofs):
succ-equiv : ℤ ≃ ℤ            -- = (succ, proof-it-is-an-equivalence)

-- 2. ua turns that equivalence into a PATH:
ua succ-equiv : ℤ ≡ ℤ

-- 3. loop is a path, so Cover must send it to a path in the universe — supply the ua-path:
Cover : S¹ → Type
Cover base     = ℤ
Cover (loop i) = ua succ-equiv i

-- transport along loop then executes as succ:
transport (λ i → Cover (loop i)) : ℤ → ℤ   ≡   succ    -- loop, run, is "+1"
Why an equivalence and not just a function: Cover sends the path loop to a path ℤ ≡ ℤ, and a path in the universe is an equivalence (univalence). So you prove succ is an equivalence, then ua manufactures the path. The proof lives one step earlier; ua is the bridge from it to the identity.

Quotients: the practical HIT

Path constructors that identify elements are where HITs earn their keep in real programs. Integers as differences of naturals:

data ℤ' : Type where
  _⊝_  : ℕ → ℕ → ℤ'                                    -- (a ⊝ b) = "a minus b"
  quot : (a b k : ℕ) → (a ⊝ b) ≡ ((a + k) ⊝ (b + k))    -- identify equal differences
  -- (+ a set-truncation constructor, so ℤ' is a set)

Now 3 ⊝ 1 and 5 ⊝ 3 are equal (both are "2"), on the nose. To define a function out, you handle the data constructor and then prove your function respects the identification:

negate : ℤ' → ℤ'
negate (a ⊝ b)        = b ⊝ a                 -- swap
negate (quot a b k i) = quot b a k i          -- OBLIGATION: negate respects quot
--   you must show   negate(a⊝b) ≡ negate((a+k)⊝(b+k))

That quot clause is the path constructor showing up in your code. This is the "no setoid hell" payoff: ℤ' is a genuine type where equal differences are literally equal, so you never carry an equivalence relation around — but every function owes a proof that it respects the identifications. The same recipe builds ℚ, finite multisets (a swap constructor), syntax modulo renaming, and so on.

What you prove, and when

StageWhat you supply / prove
Define the HITjust constructors (points, paths, higher paths). No laws. Typechecker checks positivity + endpoints/boundaries.
Map out (eliminate)one clause per constructor; for a path constructor, a path (into a set, a proof of equality) — "respect the identification"
Use a path valuecompose (∙), invert (sym), transport, ap — all free from the identity type
Establish propertiestheorems proved afterward (e.g. π₁(S¹) = ℤ)
Does it run? In cubical Agda these compute: transport … loop reduces, and the winding arithmetic executes. In book-HoTT the ua/HIT steps are axioms and get stuck. Making HIT paths run is one of the reasons cubical exists.
