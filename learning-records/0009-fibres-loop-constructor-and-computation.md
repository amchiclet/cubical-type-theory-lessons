## 1. Contractibility, and "contract a connected graph but needs extra data"

The learner's instinct was correct and worth banking precisely, because it
separates two things that look alike:
- **Path-connected** (0-connected): any two points joined by *some* path. A
  connected graph has this.
- **Contractible**: path-connected AND no nontrivial loops AND no nontrivial
  higher loops, all the way up. A center `c` plus a coherent choice of path from
  `c` to every point.

A connected graph with a cycle is path-connected but not contractible: the cycle
is a loop you cannot fill. Spanning tree contracts; each leftover edge generates
π₁. So "connected, contract it, needs extra data" is exactly right, and the extra
data measures how far *connected* is from *contractible*.

Payoff for J (reinforces Lesson 5): the based path space `Σ(y:A) (a=y)` is the
*tree*, contractible with center `(a, refl)`. Proving for `refl` suffices because
you land on the unique center of a contractible space, not because you enumerate
paths. The graph-with-a-cycle is the wrong picture for the based path space; that
space is always the tree.

## 2. Fibres and witnesses (setup Lesson 6 already relies on)

`fib_f(b) := Σ(a:A) (f a = b)`, every `a` landing on `b` packaged with a path.
- Many `a` can lead to `b` (2-to-1 gives a two-element fibre).
- The *same* `a` can appear twice, via two different paths `p, q : f a = b`, so
  `(a,p) ≠ (a,q)` unless `p = q`.
- Defined for *any* function, dependent or not.
- **Σ remembers its witness (data); `‖Σ‖` is mere existence.** Σ can have many
  elements, one per witness; truncation squashes them to one. Σ = "here is a
  specific one," `‖Σ‖` = "there is one." This is the exact distinction the
  learner was circling with "can the exists type have many witnesses."

This is precisely the Lesson 6 definition: `f` is an equivalence iff every fibre
is contractible (one preimage each, up to path). Many-element fibre = far from
invertible; empty = not hit; contractible = uniquely hit. The record confirms
Lesson 6's `isContr(fibre f b)` framing is what the learner needs; no fix, but if
Lesson 6 does not say "Σ remembers its witness" out loud, add one line there.

## 3. `loop` is a constructor, not built from `refl` (Lesson 8 touch-up candidate)

The learner is still half-stuck: "hard to see the path isn't created by refl but
magically included by all paths from refl." The fix is to run the exact
`length`/`cons` mirror the learner already trusts:
- `length : List A → ℕ` is defined by List's recursion principle: say where
  `nil` goes, where `cons` goes. `nil`/`cons` are primitive data.
- S¹ is generated by `base : S¹` (point constructor, like `nil`) and
  `loop : base = base` (**path constructor**, the new HIT move). `loop` is put in
  by hand, primitive data exactly as `base` is. It is NOT `refl` and NOT a
  `refl`-composite.
- `refl` generates only the trivial path at each point. Ordinary inductives
  (ℕ, Bool, List) have only `refl`-forced paths, which is why their identity
  types are discrete. A HIT is the move where you *declare extra paths as
  constructors*, which is what puts `loop, loop∙loop, loop⁻¹, ...` into
  `base=base`.
- Recursion out of S¹ mirrors `nil`/`cons`: to map out, "say where `base` goes
  (a point `b`), say where `loop` goes (a loop `ℓ : b=b`)." `loop` is a case you
  handle, just like `cons`.
- Caveat kept honest: a HIT *can* add a 2-path constructor forcing a path to
  equal a composite; but for S¹ `loop` is *free*, and that freedom is what gives
  π₁(S¹)=ℤ.

Lesson 8 already "bakes in the learner's worked-through confusion" (path
constructor is a constructor of S¹, not of `=`, no external injection). The
touch-up: make the `length`/`cons` <-> `base`/`loop` mirror explicit up front,
including the map-out side, since that analogy is the one that dislodges the
"magically from refl" reading. Low priority; only if revisiting Lesson 8.

## 4. Typecheck vs compute (sharpens Lesson 9 and the HoTT-vs-CTT beat)

The learner's model needed one correction. Typechecking `t : A` is not "walk both
ASTs and compare shapes"; its core op is **normalize by the computation rules
(definitional equality), then compare**. Computation = reduction: beta, plus each
eliminator's rule that fires *when it meets a constructor* (`transport` along
`refl` steps, `if` on `true` steps). A term is a value when nothing fires,
**stuck** when an eliminator sits on a non-constructor.

"Does not compute" is not "the proof side lacks reduction rules." It is specific:
`ua`/`funext` in book-HoTT are **axioms** (intro rule, no computation rule). So
`transport (ua e) x` typechecks fine but is *stuck*: `transport` wants a
`refl`-like constructor and `ua e` is opaque, so nothing fires. It never reduces
to `e x`.

- **Benefits of computing** (cubical restores these): canonicity (closed ℕ term
  reduces to a numeral; `transport (ua e) x` reduces to `e x`, so proofs run);
  definitional equalities hold on the nose (fewer transports/coherence);
  normal forms exist.
- **What a stuck axiom still gives** (book-HoTT): it still typechecks and the
  theory stays consistent, so all provable consequences hold (funext from ua,
  identity characterization, synthetic homotopy). You can still reason
  propositionally: transport along `ua e`, prove equalities. You only lose
  *execution*, not truth. You can prove `transport (ua e) x = e x`; only in
  cubical does it hold by reduction so you can evaluate it.

This is exactly the Lesson 9 "here is a stuck term" beat and the Lesson 5 /
Lesson 11 HoTT-vs-CTT split. Confirms them; no contradiction. If Lesson 9 does
not spell out "typechecking = normalize then compare, and an axiom has no
reduction rule so elimination gets stuck," that one framing sentence would help.
